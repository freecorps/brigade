# Spike S4 — Expo in the workspace

- Status: Done. Metro, Android, the iOS Simulator, an iPhone and `eas build` for both platforms verified
- Roadmap: Phase 0, S4
- Settles: RFC 0002 "Metro only needs to resolve the shared `packages/*` from the Bun workspace"; RFC 0008's open
  item on Hermes `Intl` support; RFC 0004's on-device check of `UNICODE_PROPERTY_ESCAPES` (Android and iOS)

## Question

Can an Expo app live in the Bun workspace next to the Vite+ apps and import `packages/ui`, `packages/i18n` and
`packages/schema` from source through Metro? Does a development build run, and does Hermes have the `Intl`
features `packages/i18n` uses (`PluralRules` for plural messages, `RelativeTimeFormat`, `dateStyle`/`timeStyle`)?
Does it run `packages/schema`'s full text rules, which need regex Unicode property escapes (RFC 0004, "Shared
core")?

## What was built

`apps/mobile` (`@freecorps/brigade-mobile`, private, AGPL-3.0-only): one Expo Router screen, the mobile
counterpart of the dashboard's legend. It has the severity and status badges from `packages/ui` tokens, translated
names, the plural message `incidents_active_count`, and a formatted date and relative time. It follows the system
light/dark setting and the device language (`en` / `pt-BR` through `resolveLocale`). SEV1 carries an alert glyph
and each status its own glyph, the same shapes as the dashboard's lucide icons. They are drawn with
`expo-symbols`: SF Symbols on iOS, Material Symbols on Android and web. They are decorative, since each badge is
one accessibility element labelled with its text. A dev-only `/intl` route reports what Hermes supports.

Versions: Expo SDK 58 (`expo` 58.0.19, Expo CLI 58.1.15, `expo-router` 58.0.26), React Native 0.88.0, React
19.3.0, Static Hermes 260318099.0.4, Metro 0.87.1, `@formatjs/intl-pluralrules` 6.3.16,
`@formatjs/intl-relativetimeformat` 12.3.16, `@formatjs/intl-locale` 5.3.12,
`@formatjs/intl-getcanonicallocales` 3.2.12, `expo-symbols` 58.0.4. Verified on the Android emulator (API 36, x86_64)
from Windows 11, and on the iOS Simulator (iPhone 17, iOS 27.0) from macOS 27.2 (see "iOS Simulator").

Decisions taken here:

- **App id `app.freecorps.brigade`** on both stores (`ios.bundleIdentifier`, `android.package`), the same
  `app.freecorps.*` prefix as Freecorps' other apps. Registered as an App ID under the Freecorps Apple team.
  URL scheme `brigade`.
- **`supportsTablet: false`.** Phone-first. On iPad the app runs in iPhone compatibility mode until a tablet
  layout exists.
- **Continuous Native Generation.** `android/` and `ios/` are generated by `expo prebuild` / `expo run:*` and
  gitignored. All native configuration lives in `app.config.ts`.
- **`app.config.ts`, not `app.json`**, so the splash and window background come from `packages/ui` tokens (light
  and dark), imported by path like `apps/web/vite.config.ts` does.
- **`build` is `expo export --platform android --platform ios`** (about 30 s), a Vite+ task in
  `vite.config.ts`. It is cacheable: `dist/` and `.expo/` are excluded from its inputs, and a cache hit restores
  `dist/`. It needs no emulator, Xcode or account. In CI it proves that Metro resolves every workspace import and
  that Hermes compiles the bundle. Native builds stay out of CI.
- **The entry is `src/index.ts`** (`package.json` `main`). It imports `src/intl/setup.ts` (measure, polyfill,
  measure again), then `expo-router/entry`, so nothing can format before the polyfills load.
- **Tests are plain Vite+ tests** (`vp test`, no jest-expo) for the pure logic: locale choice, theme choice and
  the `Intl` probe. React Native components are not unit-tested yet.

## Result

### Metro in the Bun workspace

It works with one line of configuration. Expo SDK 58's `getDefaultConfig` already detects the workspace. It
watches the root and every workspace, resolves from both `node_modules` folders, follows Bun's isolated-install
symlinks (`node_modules/.bun`) and reads package `exports`. `metro.config.js` only prepends the
`@freecorps/source` condition to `resolver.unstable_conditionNames`. Metro matches conditions in the order of each
package's `exports` map, where that condition comes first, so the app gets the TypeScript sources and no package
needs building (verified with no `packages/*/dist` present). Packages' `.ts`-extension relative imports and the
Paraglide `.js` output resolve as they are.

Two limits. Only `import` goes through `exports`, so a `require()` of a workspace package would miss the
condition. And `apps/mobile/tsconfig.json` sets `customConditions: ["@freecorps/source", "react-native"]`, keeping
Expo's own condition.

`vp check` from the root type-checks and lints `apps/mobile` with tsgo, React Native types and Expo Router's
included, with no exclusion. `expo/types` comes in through `compilerOptions.types`, because the generated
`expo-env.d.ts` is gitignored and absent on a clean checkout.

What needed a decision or a workaround:

- **React versions.** Expo SDK 58 pins `react` 19.3.0 and `apps/web` uses 19.3.1. Bun's isolated installs keep
  them apart: each app, and `react-native`, resolves its own copy. No root override was needed.
- **Optional peers get installed and autolinked.** Bun installs `expo-router`'s optional peers
  (`react-native-reanimated`, `react-native-worklets`, `react-native-gesture-handler`, the last at 3.4.0 rather
  than SDK 58's 3.3), and autolinking then compiled them. That added about 2 GB of native build output, with
  versions that do not match the SDK. The app uses none of them yet, so `package.json` excludes them from
  autolinking (`expo.autolinking.exclude`). When the app needs Reanimated, add the three with `expo install` and
  drop the exclusion.
- **`npx` does not work in this repository.** npm refuses to run because the root `devEngines` names Bun. Use
  `bunx expo …` or the package scripts.
- **Windows only: native builds hit the 260-character path limit.** The CMake 3.22.1 that AGP uses by default
  ships Ninja 1.10, which fails to create object files under `node_modules/.bun/<pkg>@<version>+<hash>/…`. Fix:
  CMake 3.31.6 from the Android SDK repository (Ninja 1.12, long-path aware), selected with `cmake.dir` in the
  generated `android/local.properties`. `git clean` of a built tree also needs `-c core.longPaths=true`. macOS,
  Linux and EAS are not affected.
- **The emulator cannot reach Metro over the LAN** on this machine (Windows firewall). `adb reverse tcp:8081
  tcp:8081` plus the dev-client URL with `127.0.0.1` works.
- **`Link asChild` drops a `Pressable` style function.** Style the pressed state from the `Pressable`'s
  render-function children instead (`src/screens/overview.tsx`).
- **Changing the language or theme while the app runs works.** Checked with screenshots every 2 to 4 seconds
  after `cmd locale set-app-locales` and `cmd uimode night yes|no`. The screen redraws in the new language or
  theme within one interval and is never left blank. Three blank screenshots from the first round had two other
  causes. First, a development cold start on this emulator takes about 30 seconds: the window ground, then a black
  frame while the dev launcher hands over to the app, then the screen. Those shots were taken about 10 seconds in.
  Second, another app was sharing the emulator and took the foreground. Release builds embed the bundle, so their
  cold start is not measured by this; check it with the first `preview` build.

### Hermes `Intl` on Android

Measured by `src/intl/probe.ts`, which uses each feature and compares the output, before and after the polyfills
load (screenshot `android-intl`):

| Feature                                  | Hermes (Android, RN 0.88)                        | With polyfills               | Used by                                         |
| ---------------------------------------- | ------------------------------------------------ | ---------------------------- | ----------------------------------------------- |
| `Intl.PluralRules`                       | **Missing**                                      | Works (`@formatjs`, en + pt) | every plural message (`incidents_active_count`) |
| `Intl.RelativeTimeFormat`                | **Missing**                                      | Works (`@formatjs`, en + pt) | `formatRelativeTime`                            |
| `Intl.Locale`                            | **Missing**                                      | Works (`@formatjs`)          | the two polyfills above                         |
| `DateTimeFormat` `dateStyle`/`timeStyle` | Works                                            | native                       | `formatDateTime`                                |
| `DateTimeFormat` `timeZone` (IANA)       | Works                                            | native                       | `formatDateTime`                                |
| `Intl.NumberFormat` (en, pt-BR)          | Works                                            | native                       | `formatNumber`, `{count: number}`               |
| Regex Unicode property escapes (`\p{…}`) | **Works** (`UNICODE_PROPERTY_ESCAPES` is `true`) | not polyfilled               | `v.string` in `packages/schema`                 |

Without the `PluralRules` polyfill a plural message does not fall back. Paraglide's registry throws while
rendering (`WeakMap key must be an Object`), which takes down the screen. The polyfills load in
`src/intl/polyfills.ts`, imported by the entry file before Expo Router. They are getCanonicalLocales, Locale, PluralRules
with `en` and `pt` data, and RelativeTimeFormat with `en` and `pt` data. Each one installs itself only when the
engine lacks the feature. After loading, the helpers render "No active incidents / 1 active incident / 1,284
active incidents", "Nenhum incidente ativo / 1 incidente ativo / 1.284 incidentes ativos", "Oct 24, 2026, 8:57
PM" / "24 de out. de 2026, 20:57", "3 hours ago" / "há 3 horas" and "yesterday" / "ontem". CLDR's `pt` data is
Brazilian Portuguese.

**Regex property escapes.** `UNICODE_PROPERTY_ESCAPES` from `@freecorps/brigade-schema` is `true` on this
Hermes, so the client runs the same full text rules as the server, not the fallback. The `/intl` screen also runs
two incident titles through `v.string({ min: 1, max: INCIDENT_TITLE_MAX })`, the validator `incident.declare`
uses. "Checkout down 🔥" is accepted. "Checkout" + U+200B (zero-width space) + "down" is rejected ("Contains
control, invisible or bidi characters"). Both match the server and the Node test (`src/lib/text-samples.test.ts`).

iOS gives the same results (see "iOS Simulator").

### iOS Simulator

Run on an iPhone 17 Simulator (iOS 27.0, 24A5423a) from macOS 27.2 with Xcode 27.0 beta 6 (27A5252f), CocoaPods
1.17.0 and Ruby 4.0.7. Same app, versions and Hermes (260318099.0.4) as on Android.

What it took:

- **`bunx expo run:ios` works with no workaround in the repository.** Prebuild generates `ios/` with bundle id
  `app.freecorps.brigade`. CocoaPods resolves every pod through Bun's `node_modules/.bun` symlinks.
  `react-native-safe-area-context`, `react-native-screens` and `RNCMaskedView` autolink and build from source.
  Reanimated, Worklets and Gesture Handler stay out (`expo.autolinking.exclude`). Prebuild prints "Updating
  package.json", then "no changes": `package.json` is not rewritten. The development build takes about 2 minutes
  from a clean `ios/`, pod install included, because React Native core and Hermes come prebuilt.
- **The Xcode must have a Simulator runtime for its own iOS SDK.** This Mac also had Xcode 26.6 (iOS 26.5 SDK)
  selected, with only the iOS 27.0 runtime installed. `xcodebuild` then finds no destination ("Unable to find a
  destination matching the provided destination specifier"). `DEVELOPER_DIR=<Xcode 27>/Contents/Developer bunx
  expo run:ios` builds with the matching Xcode without changing `xcode-select`. Installing the runtime for the
  selected Xcode (`xcodebuild -downloadPlatform iOS`) is the other way.
- **Fixed: the launch screen ignored the splash ground.** Without a splash image, `expo-splash-screen` 58.0.11
  writes the light and dark ground into the `SplashScreenBackground` colour set but leaves `SplashScreen.storyboard`
  on the template's `systemBackgroundColor`. The cold start was pure white or black, then the app drew `#f7f7f5` or
  `#121211`. `plugins/splash-ground.ts`, a config plugin applied from `app.config.ts`, points the launch view at
  the colour set as `expo-splash-screen` does when there is an image. Remove it once the app has a splash image.
  Its test runs `expo-splash-screen`'s own storyboard helpers on the SDK 58 bare template's storyboard; they are
  loaded by file path, since the package does not export them.
  Checked by recording one cold start per theme (stills `ios-splash-light` and `ios-splash-dark`). Light keeps
  `#f7f7f5` from launch to the first app frame. Dark keeps `#121211` through the launch screen. That is apart from
  about 60–90 ms of the development client's launcher in both themes (light 4.12–4.21 s, dark 4.04–4.10 s in the
  recordings). Dark then shows about 145 ms of pure black (4.80 s to 4.95 s) while the development client hands
  over to the app, before the app draws `#121211` (`ios-cold-start-dark-handover`: only the dev client's Tools button is
  drawn). That gap is most likely the development build's: it comes from the handover, like the black frame seen
  on Android, and no `preview` build was run to rule it out. Release builds embed the bundle, so check it with the
  first `preview` build. Android was not affected by the storyboard issue.
- **Fixed: the `/intl` probe reported `dateStyle`/`timeStyle` as missing.** iOS's Hermes formats them correctly
  but joins medium date and short time with " at " ("Mar 5, 2026 at 2:30 PM"), where Android and Node print ", ".
  That is locale data, not support, so `src/intl/probe.ts` accepts both joiners. No `@formatjs` date or number
  polyfill is needed.

Hermes `Intl` on iOS, measured by the same probe (screenshot `ios-intl`):

| Feature                                  | Hermes (iOS 27 Simulator, RN 0.88)               | With polyfills               |
| ---------------------------------------- | ------------------------------------------------ | ---------------------------- |
| `Intl.PluralRules`                       | **Missing**                                      | Works (`@formatjs`, en + pt) |
| `Intl.RelativeTimeFormat`                | **Missing**                                      | Works (`@formatjs`, en + pt) |
| `Intl.Locale`                            | **Missing**                                      | Works (`@formatjs`)          |
| `DateTimeFormat` `dateStyle`/`timeStyle` | Works (joins with " at ")                        | native                       |
| `DateTimeFormat` `timeZone` (IANA)       | Works                                            | native                       |
| `Intl.NumberFormat` (en, pt-BR)          | Works                                            | native                       |
| Regex Unicode property escapes (`\p{…}`) | **Works** (`UNICODE_PROPERTY_ESCAPES` is `true`) | not polyfilled               |

"Checkout down 🔥" is accepted and "Checkout" + U+200B + "down" rejected, as on Android. The helpers render the same
strings as on Android except the date: "Oct 24, 2026 at 11:39 PM" in `en`; `pt-BR` is "24 de out. de 2026, 23:40"
on both (`ios-intl-rendered`, `ios-intl-rendered-pt-BR`). `/intl` never hung; the app sat idle once drawn.

The checklist, each item passed:

1. Build and launch: as above.
2. The overview renders the workspace packages from source: badges with glyphs, plural rows, date and relative
   time (`ios-light-en`).
3. Light and dark follow the system while the app runs (`xcrun simctl ui booted appearance dark|light`), and the
   launch screen shows each theme's ground after the fix above (`ios-dark-en`, `ios-splash-light`,
   `ios-splash-dark`; the development-only black gap in dark is described there).
4. `pt-BR` (`ios-light-pt-BR`, `ios-dark-pt-BR`). The built `Info.plist` has `CFBundleLocalizations` `en` and
   `pt-BR`. The language was set per launch with `xcrun simctl launch booted app.freecorps.brigade
   -AppleLanguages "(pt-BR)" -AppleLocale pt_BR`, not through Settings → Apps → Brigade → Language.
5. `/intl`: the table above.
6. Safe areas: the header sits below the Dynamic Island, content never scrolls under the status bar, and the last
   card clears the home indicator (`ios-safe-area-bottom`).
7. Reduce Motion (`xcrun simctl spawn booted defaults write com.apple.Accessibility ReduceMotionEnabled -bool
   true`, then relaunch): pushing `/intl` cross-fades in place instead of sliding (`ios-reduce-motion-fade` against
   `ios-push-slide`, stills from a screen recording of each). From the recording's frame timestamps, 10 to 90 % of the change takes about 300 ms and the eased whole about 650 ms.
8. Dynamic Type at `accessibility-extra-extra-extra-large`, pt-BR: text grows, rows grow and badges wrap one per
   line. The whole overview, top to end, was captured in overlapping pages (`ios-dynamic-type-xxxl-pt-BR` and
   `-1` to `-6`, `-7-end` at the end of the scroll) and nothing clips; the last card clears the home indicator.
   Set with `xcrun simctl ui booted content_size`, it applied on the next launch, not to the running app; a live
   change from Settings was not tried. The badge glyphs keep their fixed size (`fontSize.sm`) and the gap between
   code and name stays `spacing[1]`, so at this size they look small; scaling them with the text is left for when
   the badges get real use. `/intl` was not checked at this size.

How it was driven: on this beta runtime, XCTest-based input (taps, swipes, the "Open in Brigade?" prompt that
`xcrun simctl openurl brigade://intl` raises) timed out, so no screen was reached by tapping. `/intl` and the
rest of the overview were reached with a temporary `router.push("/intl")` and `scrollTo`/`scrollToEnd` in a
development build, not committed. Screenshots come from `xcrun simctl io booted screenshot` once the app was drawn in the
foreground, and each was checked by eye.

## Decision

Keep Expo with Metro for mobile (RFC 0002 unchanged in substance): no custom resolver, only the
`@freecorps/source` condition. Ship the four `@formatjs` polyfills with `en` and `pt` data, loaded before
anything formats. Add locale data for each new locale. Revisit when Hermes ships `PluralRules` and
`RelativeTimeFormat`: the polyfills step aside on their own, so the only cost of keeping them is bundle size.

## EAS Build

`eas.json` has `development` (dev client, internal distribution), `preview` (internal) and `production`
(auto-incremented build numbers, versions kept remotely). Each sets `EXPO_PUBLIC_BRIGADE_ENV` as a placeholder
until the app talks to an API, and pins Bun 1.4.4 like `devEngines`. The EAS project is
`@freecorps/brigade`, owned by the Freecorps organisation. `eas init` cannot write to a dynamic config, so
`owner` and `extra.eas.projectId` are set by hand in `app.config.ts`; the project id is not a secret.

Both `development` builds succeeded on EAS from the same commit (Expo SDK 58, build number 1):

- **Android** (`--platform android --non-interactive`): EAS generated and keeps the upload keystore. EAS
  installed Bun 1.4.4 over its image's 1.4.2, detected `apps/mobile` as a Bun workspace member and installed
  from `bun.lock` at the repository root. The APK installed on the Android emulator (API 36), loaded the bundle
  from Metro, and the incident list connected (`Live`), importing `packages/*` from source.
- **iOS** (interactive, Freecorps Apple team): EAS found the App ID
  `app.freecorps.brigade`, reused the team's existing distribution certificate and created an ad hoc
  provisioning profile. `ios.config.usesNonExemptEncryption: false` is now in `app.config.ts`: the app only
  uses standard encryption (HTTPS, and Apple's CryptoKit for push payloads in spike S1), so EAS and App Store
  Connect stop asking on every build. The build (build number 1) was then installed on the project owner's
  iPhone. The dev client loaded the bundle from the local dev
  server over the LAN and the incident list was live; the owner confirmed it works on the phone.

EAS syncs the App ID's capabilities with the entitlements the config declares. The config declares none yet, so
the iOS build turned Push Notifications, Time Sensitive Notifications and App Groups off on the App ID; they come
back when S1 adds the notification entitlements.

Registering a test iPhone uses `bunx eas-cli@latest device:create`, followed by a new iOS build.

**Local builds are the default.** Each cloud build spends EAS build credits, so builds run on our own machines
and EAS is used for the credentials it keeps and, later, for submission. Cloud builds are only for when EAS
must create or regenerate credentials. Two root tasks (details in `apps/mobile/README.md`):

- `vp run mobile:install`: `expo prebuild`, then `xcodebuild` or Gradle, then install on a phone with
  `xcrun devicectl` or `adb`. The development variant is the dev client; the release variant embeds the
  JavaScript. iOS signs with Xcode automatic signing through the Freecorps team's account in Xcode, and Android
  with the debug key. It uses the newest installed Xcode: Expo SDK 58's template already has a UIScene
  delegate, so the iOS 27 SDK does not trap at launch.
- `vp run mobile:build`: `eas build --local` for an `eas.json` profile, with EAS's remote credentials. Artifacts
  go to `~/brigade-builds`, outside the repository. `preview` now builds an APK on Android (internal
  distribution), and `production` builds use the newest released Xcode, because App Store Connect rejects beta
  builds.

Both tasks are declared in the root `vite.config.ts` with `cache: false`. A cached `vp run` task runs under
Vite+'s file-access tracking, and under it Gradle cannot start the shebang-less `prefab_command` scripts AGP 9
writes for CMake ("error=8, Exec format error"). The same build from a plain shell works. `eas build --local`
also needs its build plugin installed with Bun, because eas-cli starts it with `npx` and npm refuses to run under
the root `devEngines`; `scripts/mobile-build.mjs` does that. EAS's own `expo doctor` step still fails on npm for
the same reason, and EAS carries on past it.

Verified on macOS 27.2 with the Android emulator (API 36): `mobile:build --profile preview` made an APK signed
with EAS's keystore, which `mobile:install --from` installed and opened. `mobile:install` built and installed the
release variant (sync unavailable, as expected without `EXPO_PUBLIC_BRIGADE_SYNC_URL`) and the development
variant, which went `Live` against Metro and the local dev server. On iOS, the Release build compiles with Xcode
27 beta 6 (unsigned, JavaScript embedded). Not done yet:

- **Signing with Xcode's account.** Xcode 27 beta reported "No Accounts" although Xcode 26.6 has the team's
  account, and Xcode 26.6 cannot build here without its iOS 26.5 platform. Signing in to Xcode 27 should fix it.
- **`mobile:build` for iOS.** The archive failed: the EAS ad hoc profile "doesn't include signing certificate
  Apple Distribution: …". EAS's credential check had passed. Most likely, xcodebuild picked the Apple Distribution
  certificate in the login keychain, a different one from EAS's, over the one in EAS's temporary keychain.
  Compare the two (`bunx eas-cli@latest credentials -p ios`) before the next iOS build.
- **A physical iPhone or Android phone** through the scripts.

Store submission (`eas submit --path <artifact>`) waits for Phase 4 (after the CLA).
