# RFC 0008 — Internationalization

- Status: Draft

## Scope

Every user-facing surface is localized: web dashboard, mobile app, public site/docs, Slack messages, push
notifications, emails, status pages. Launch locales: `en` (source) and `pt-BR`.

## Decisions

- **One catalog package** (`packages/i18n`), consumed by web, mobile and server. Messages use the inlang
  message-format syntax (`{param}`, and `declarations`/`selectors`/`match` for plurals), compiled by Paraglide.
- **Source language is English**; keys are semantic and snake case (`incident_status_investigating`), not English
  sentences.
- **Server-rendered messages are localized per recipient**, not per workspace: Slack DMs, emails and push use the
  recipient's locale stored on their user/device profile. Shared Slack channels use the workspace default locale.
  Built for emails: a user's `locale` (D1 `user.locale`, Better Auth's `additionalFields`, only `en` or `pt-BR`) is
  set at sign-up by the dashboard (its current language; else the closest to `Accept-Language`) and by its language
  switch, and the email notifier renders each email in it, English when unset (RFC 0005 "Email"). The mobile app
  does not send it yet; push text has no words to translate yet (codes and the incident's title, RFC 0006).
- **Push and encryption:** the instance renders the notification text in the device's locale before encrypting
  (RFC 0006), so the NSE only decrypts and displays.
- **Dates, durations and numbers** via standard `Intl` (Workers, browsers; Hermes with polyfills, see below).
- **Domain values stay canonical** in data and API (`sev1`, `investigating`); only the UI translates them.
- **User content is not translated** (incident titles, updates). Optional AI translation is a later feature.

## Library: Paraglide JS

Chosen over i18next and Lingui because:

- **Compiles messages to plain typed functions** (`m.incident_declared({ number })`) — no runtime catalog loader,
  one module per message, so bundles keep only the messages they import (matters for Workers size limits and
  mobile startup). `m.x` through the `m` namespace shakes under Vite/Rolldown but not under esbuild (Wrangler),
  so server and Worker code imports messages by name from `@freecorps/brigade-i18n/messages`.
- **Explicit locale per call** (`m.incident_declared(params, { locale: "pt-BR" })`). The server renders Slack DMs,
  emails and push text for each recipient's locale without request-global state.
- **Framework-agnostic output**: the same compiled package works in Workers, the React dashboard, TanStack Start
  (site/docs, which has an official Paraglide example) and React Native.
- Type errors when a key or parameter is missing.

`packages/i18n` holds the message sources (one JSON file per locale) and exports the compiled functions plus
`Intl` helpers. It compiles in its own build and ships the precompiled output, so consumers never run the
Paraglide Vite plugin. The server passes `{ locale }` on every call and never sets a global locale. The runtime uses
strategy `["globalVariable", "baseLocale"]` with AsyncLocalStorage disabled: it reads no cookies, storage or URL,
so it is safe in Workers and React Native, and UIs persist the chosen locale themselves.

**Hermes (spike S4, [write-up](../spikes/s4-expo-workspace.md)).** On Android with React Native 0.88, Hermes has
`DateTimeFormat` (including `dateStyle`/`timeStyle` and IANA time zones) and `NumberFormat`. It has no
`Intl.PluralRules`, `Intl.RelativeTimeFormat` or `Intl.Locale`. Without `PluralRules`, rendering a plural message
throws. The mobile app therefore loads the `@formatjs` polyfills for getCanonicalLocales, Locale, PluralRules and
RelativeTimeFormat before anything formats, with locale data for `en` and `pt` only. Each polyfill installs itself
only when the engine lacks the feature. A new locale adds its data there. iOS (Simulator, iOS 27) gives the same
results; its locale data joins a medium date and time with " at " ("Mar 5, 2026 at 2:30 PM") where Android prints
", ".

## Site and docs

Public site and docs in `apps/site`, built with Fumadocs on TanStack Start, with per-locale routes
(`/en/...`, `/pt-br/...`) using Fumadocs' i18n support. Prerendered pages must be listed per locale.
Translation workflow: PRs to catalogs; consider Weblate/Crowdin (free tiers for open source) once the community grows.
